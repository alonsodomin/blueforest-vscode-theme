# AGENTS.md

## Layout
- Nix flake monorepo of BlueForest theme ports. `modules/<app>/` is a self-contained flake; its `flake-module.nix` is both imported by the app flake and published as `flakeModules.default` for the root `flake.nix` to compose.
- Implemented apps: `modules/vscode` (VS Code/VSCodium extension), `modules/bat` (TextMate theme), `modules/neovim` (Neovim colourscheme and lualine theme), `modules/starship` (Starship preset), `modules/opencode` (OpenCode theme), and `modules/sbt` (sbt prompt).
- The VS Code extension is theme-only: `package.json` has no `main`, and there is no JS to build, test, or lint. Node and `vsce` are only for packaging.
- Theme files are hand-edited sources, not generated: `modules/vscode/themes/Blueforest-color-theme.json`, `modules/bat/themes/BlueForest.tmTheme`, `modules/neovim/themes/blueforest.lua`, `modules/neovim/themes/lualine-blueforest.lua`, `modules/starship/themes/blueforest.toml`, and `modules/opencode/themes/blueforest.json`. Checks compare packaged copies against them. `modules/sbt` is the exception: it does not define a theme, it installs the upstream `sbt-prompt` plugin and selects its `BlueforestTheme` from `modules/sbt/config/`.
- `README.md` is the consumer-facing contract (outputs, install snippets, identifiers). Update it when outputs or module behavior change.

## Verify
- Format: `nix fmt` (nixfmt, taplo, prettier for `*.json`, stylua for `*.lua`, shfmt with tabs, shellcheck).
- Fast checks: `nix flake check` at the root (includes `treefmt`). Per app: `nix flake check ./modules/vscode`, `nix flake check ./modules/bat`, `nix flake check ./modules/neovim`, `nix flake check ./modules/starship`, `nix flake check ./modules/opencode`, `nix flake check ./modules/sbt`. CI runs all seven.
- Two checks build an editor and are only run on purpose: `BLUEFOREST_VSCODE_INTEGRATION_CHECK=1` (VSCodium) and `BLUEFOREST_NEOVIM_NIXVIM_CHECK=1` (nixvim). Both need `--impure`, because they read the environment. The CI sets both, so they run there. `nix build .#vscode-integration-check` and `nix build .#neovim-nixvim-check` build them on their own.
- Single check: `nix build .#checks.x86_64-linux.<name>`, where `<name>` is `version`, `overlay`, `treefmt`, `vscode-extension`, `vscode-configuration`, `bat-theme`, `bat-theme-home`, `bat-theme-nixos`, `neovim-theme`, `neovim-configuration`, `neovim-module`, `starship-preset`, `starship-render`, `starship-wrapper`, `starship-module`, `opencode-theme`, `opencode-configuration`, `opencode-module`, `sbt-package`, or `sbt-module`.
- The VSCodium integration check is intentionally absent from `nix flake check`. Run `BLUEFOREST_VSCODE_INTEGRATION_CHECK=1 nix flake check --impure` or `nix build .#vscode-integration-check` (expensive).
- The root flake owns the pin of nixvim (`inputs.nixvim`), and the application follows it (`inputs.neovim.inputs.nixvim.follows = "nixvim"`). The application keeps a pin of its own in `modules/neovim/flake.lock`, for the consumers that take it on its own. `nix flake lock` does not re-resolve the inputs of a path input: use `nix flake update neovim` after adding a `follows` to it.
- Root flake evaluation only sees tracked files. `git add` new files before running `nix flake check` or `nix build .#...`.
- Shells: `nix develop` (root tools + `release`), `nix develop .#vscode` (nodejs/vsce; provides `package`, `nixfmt`), `nix develop .#neovim` (neovim/stylua/nixfmt), `nix develop .#starship` (starship/taplo/nixfmt), `nix develop .#opencode` (opencode/jq/nixfmt), `nix develop .#sbt` (sbt/nixfmt).

## Versions and releases
- One shared version. `VERSION`, every `modules/*/VERSION`, and every `modules/*/package.json` must match (`tests/version.nix`). `modules/vscode` has no `VERSION` (package.json is its copy); the `neovim` `VERSION` file does exist, so include it in manual bumps.
- Prefer the helper over hand-editing: `release vscode` from `nix develop`, or `nix run .#release -- vscode`. It is interactive, needs authenticated `gh` and network, pushes, and triggers CI; do not run it unattended.
- The helper discovers applications from `tools/lib/*.sh`; `vscode.sh`, `starship.sh`, `opencode.sh`, and `neovim.sh` exist. `release bat` fails and `release all` currently releases only VS Code, Starship, OpenCode, and Neovim. Bat versions/changelogs are edited by hand and published by `release-bat.yml`.
- Changelogs: `modules/<app>/CHANGELOG.md`, newest section first, heading `## X.Y.Z - [DD-MM-YYYY]`. Root `CHANGELOG.md` links to the app changelogs and has an `Unreleased` section.
- Release workflows: `.github/workflows/release.yml` dispatches to `release-<app>.yml`; tags are `vscode/<version>`, `bat/<version>`, `neovim/<version>`, `starship/<version>`, `opencode/<version>`.

## Conventions and traps
- Split licence: `modules/*/themes/**`, images, and `*.md` are CC BY 4.0; Nix, scripts, workflows, and manifests are MPL-2.0. New code/config files start with `# SPDX-License-Identifier: MPL-2.0`. `NOTICE.md` maps paths.
- Shell is bash and uses tabs (`treefmt.nix`: shfmt `indent_size = 0`, `simplify = false`); shellcheck must pass.
- Identifiers: theme ID `BlueForest`; extension ID `alonsodomin.blueforest-theme`; nixpkgs attr `blueforest-vscode-theme`; bat theme name `BlueForest`; Neovim package `blueforest-neovim-theme`; Neovim colourscheme name `blueforest`; lualine theme name `blueforest`; Starship preset name `blueforest`; Starship packages `blueforest-starship-preset` and `blueforest-starship`; OpenCode theme name `blueforest`; OpenCode package `blueforest-opencode-theme`; sbt package `blueforest-sbt-prompt`; sbt theme `BlueforestTheme` from the upstream `sbt-prompt` plugin. Note the lowercase `f` in `Blueforest-color-theme.json`.
- The VS Code module exists twice and must stay in sync: the exported modules in `modules/vscode/flake-module.nix`, and the copy evaluated by `vscode-configuration` in `modules/vscode/nix/modules/default.nix` (which imports `nix/overlay.nix`). The comment in `default.nix` names the old `pkgs.blueforest-theme`; the real attr is `pkgs.blueforest-vscode-theme`.
- The VSIX build uses `vsce package --no-dependencies`; `.vscodeignore` decides what ships. Keep dev files out and add new runtime files explicitly. `*.vsix` is git-ignored.
- `.vscode/launch.json` still points at the old `vscode/` path; don't rely on F5. Use `code --extensionDevelopmentPath=$PWD/modules/vscode` or package the VSIX.
- Root aggregate modules are explicit: `flake.nix` currently composes the VS Code, Starship, OpenCode, sbt, and Neovim overlay/modules in `overlays.default` and `homeModules.default`; bat ships packages/checks only, and sbt has no NixOS module because sbt has no system-wide configuration directory.
- The Neovim package is a plugin (`vimUtils.buildVimPlugin`), so that the colourscheme is at `colors/blueforest.lua` and the theme of lualine at `lua/lualine/themes/blueforest.lua`, which are the two places Neovim and lualine read them from. The plugin directory of the runtimepath is named after the `pname`, not after the store path of the derivation.
- The Neovim module adds the theme to `programs.neovim.plugins` with `lib.mkDefault`, and does not select the colourscheme: Home Manager drops `extraConfig` when the consumer sets `initLua`, so the selection belongs to the consumer's own configuration (`vim.cmd.colorscheme("blueforest")`).
- The nixvim module (`modules/neovim/nix/nixvim.nix`) is imported *into* the configuration of nixvim (`programs.nixvim.imports`), not into the configuration of the system: nixvim builds an instance of nixpkgs of its own, so it has to add the overlay of the theme itself. It only uses three option names of nixvim (`nixpkgs.overlays`, `extraPlugins`, `colorscheme`), so it does not depend on the version of nixvim; only the check does.
- lualine finds the theme of the statusline on its own: its `auto` theme looks the theme up by the name of the colourscheme, and both are `blueforest`. Only the sections of the statusline are configuration.
- The theme of Neovim defines the seven `RainbowDelimiter*` groups, because the rainbow-delimiters plugin reads their colours from the colourscheme. A group the theme does not define leaves the rainbow without a colour.
- The OpenCode module needs `programs.opencode.cli`, which Home Manager gained in commit `6d9655f764`; the `home-manager` input of the root flake is pinned to a revision that has it.
- The OpenCode module does not enable OpenCode: Home Manager writes the theme and the settings of the terminal only when the program is enabled, so the consumer decides.
- Home Manager's `programs.opencode.themes` only takes a path, never a store path string: give it a path literal, or the theme is taken for a JSON object and regenerated.
- OpenCode ignores a theme it cannot read, and it ignores it silently: a missing token or a colour that does not resolve makes it fall back to the theme it ships with. The checks of the application stand in for it, because a TUI cannot be rendered in a build.
- The root `overlays.default` composes with `lib.composeManyExtensions`, not by hand: an overlay takes `final` and `prev`, and folding them by hand loses one of the two. `tests/overlay.nix` guards the result.
- The sbt prompt is not defined here: `modules/sbt/config/` only declares `com.github.alonsodomin:sbt-prompt` and selects `BlueforestTheme`. Keep it that way; the prompt and the palette live upstream at <https://github.com/alonsodomin/sbt-prompt>.
- sbt has no release workflow: the prompt and its theme are provided by the upstream plugin, so there is nothing to publish here. Do not add `tools/lib/sbt.sh` or a `release-sbt.yml`.
- The sbt Home Manager module is optionless and inert unless `programs.sbt.enable = true`. It writes `~/.sbt/1.0/plugins/sbt-prompt.sbt`, `~/.sbt/1.0/blueforest-prompt.sbt`, `$XDG_CONFIG_HOME/sbt/2/plugins/sbt-prompt.sbt`, and `$XDG_CONFIG_HOME/sbt/2/blueforest-prompt.sbt`. `home.packages = [ pkgs.blueforest-sbt-prompt ]` alone does not install them.
- sbt 1 reads its global base from `~/.sbt/1.0`; sbt 2 uses `$XDG_CONFIG_HOME/sbt/2`. In both, `plugins/` holds plugin declarations and the base itself holds the settings that can use them.

## Adding an application
Mirror `modules/bat` (the simplest app) or `modules/starship` (a package with an overlay and modules): create `flake.nix`, `flake-module.nix`, `devshell.toml`, `VERSION`, `CHANGELOG.md`, and the theme. Then register it in root `flake.nix` (path input with `follows` + `inputs.<app>.flakeModule`), expose it in the root aggregate modules if it provides one, add it to the CI matrix in `.github/workflows/ci.yml`, add `tools/lib/<app>.sh`, add `.github/workflows/release-<app>.yml` plus a dispatch job/input in `release.yml`, and update `README.md`, root `CHANGELOG.md`, and `NOTICE.md`.
